## 12주차: Trusted Execution Environment

- **Intel SGX (Software Guard Extensions)**
    - Intel **CPU**에서 제공하는 **하드웨어 기반** Trusted Execution Environment (TEE) 기술
        - 애플리케이션의 일부분을 격리된 **보호 영역(enclave)**에서 실행함으로써  
        **confidentiality(암호화), integrity(하드웨어 기반의 메모리 격리)**를 보장
    - Trusted Part: OS와 가상머신도 신뢰하지 않는다
    - **Enclave: 격리된 신뢰 가능한 영역 → 일부 코드와 데이터를 enclave에 로드해 실행**
        - DRAM 안의 Processor Reserved Memory (PRM) 영역 안, 전용 물리 메모리 영역인 **EPC (Enclave Page Cache)** 사용
            - EPC type: **SECS(enclave metadata)**, TCS(enclave thread 정보), 등
            - 이렇게 어떤 물리 메모리를 **EPC**로 쓰겠다라고 하는 것은 **Page Table**에 표시함
                - PT는 OS가 관리하는데, 지금 OS는 신뢰할 수 없으니까, EPC 영역에 대한 연산이 바뀔때마다 매번 HW적으로 **검증**
                    > ◆ SECS에 있는 enclave의 base, size를 참고하여 EPC page가 적합한 virtual address range**(ELRANGE)**에 맵핑되어 있어야 함
        - 4kb page단위로 쪼개서, enclave instance를 만들어서 사용함 → 각각의 enclave에 대한 상태 정보인 **EPCM**이 있음
        - **EPCM(Enclave Page Cache Map) = metadata**
            - EPC에 대한 접근이 발생하면 CPU가 **EPCM (permission 등)을 체크하고 allow**◆
        - Enclave 전용 instruction을 제공함 → 일반적인 memory instruction으로 변조하는 것을 차단
            - ECALL: enclave로 들어가기, OCALL: 나가기
            - EENTER: 일반 코드가 enclave를 호출하면 CPU는 하드웨어적으로 컨텍스트를 전환하여 enclave 모드로 진입
    - Enclave 안에서 쓸 수 있는 Library OS에 대한 연구
        - Haven[OSDI’14], SCONE[OSDI’16], Graphene-SGX[ATC’17]
    - SGXBounds [EuroSys’17]
        - Intel SGX enclave 자체는 **그 안에서 동작하는** 코드/데이터에 대해 **spatial memory safety**를 제공해주지 않음
        - Key Idea: EPC가 작은 물리 메모리를 사용하니까, address space 자체가 작다
            - (64bit system) **32bit만 pointer로 사용**하고, 상위 32bit는 pointer가 가리키는 object의 Upper bound(4byte) 저장
            - object의 Upper bound의 바로 다음 word에 Low Bound(4byte)를 저장하자
                - 즉, Register Arithmetic 연산 & 메모리 연산으로 bound checking 가능 → spatial memory safety 보장
    - **ARMv9 Realm [렐름] = enclave와 같은 역할**
        - SHELTER [Security’23]

> <span style="background-color:#e9d5b8">**Intel SGX의 Enclave**</span>  
- EPC (Enclave Page Cache): 물리적으로 격리된 메모리
- MEE (Memory Encryption Engine): 메모리 외부로 나가는 데이터는 항상 암호화
- CPU 내부 접근 제어: 소프트웨어가 아닌 하드웨어 수준에서 강제 격리
- EPCM(Enclave Page Cache Map) 검증: enclave와 페이지 간 소유권 일치 여부 확인

> <span style="background-color:#e9d5b8">**SGX-Shield: Enabling Address Space Layout Randomization for SGX Programs [NDSS'17]**</span>  
- SGX 환경에서 **MPTEE**가 요구하는 보안 특성 중 하나인 **Execution Only Memory(실행 전용 메모리, EOM)** 또는 **Execute-Only Memory(XOM)** 문제
    - ※ MPTEE(Memory Protection in Trusted Execution Environment)
    - **소프트웨어 기반 DEP (Data Execution Prevention)** 기법으로 우회적으로 구현함
        - NRW Boundary를 하나 설정해두고, 해당 주소보다 낮은 주소에는 쓰기/읽기 접근이 불가능하도록 강제
            - 코드 영역은 NRW 경계 아래에 위치, 데이터는 그 위에 위치시킴
            - 코드 페이지는 SGX 레벨에서는 RWX지만, 실제로는 접근을 모두 소프트웨어 레벨에서 막음

- **ARM TrustZone**
    - EL0=유저, EL1=커널, EL2=하이퍼바이저, **EL3=SecurityMonitor/Firmware**
    - Non-secure = Normal world (REE) / **Secure = Trusted world (TEE)**
        - Normal world → <span style="background-color:#e9d5b8">**SMC (Secure Monitor Call)**</span> → Trusted world
    - page도 다르고, cache도 구분해서 hit하고, TLB도 구분하고, 
    - memory 앞에 controller를 둠: TZASC - access control로 접근 제어
        - enclave는 encryption했기 때문에 읽어가도 괜찮음
        - enclave는 CPU 안에서 일어나는거라서, GPU 같은 곳에서는 적용이 안된다? 하지만 ARM TZ은 앞에 controller만 두면 된다?
    - <span style="background-color:#e9d5b8">**Boomerang [NDSS’17]**</span>
        - **신뢰할 수 없는 Normal World가 제공하는 악의적인 pointer를 Secure World가 따라가면서 발생하는 공격**
        - 취약점: Untrusted Application에서 sanitizer 검증을 받지 않은 pointer를 Trusted Application으로 넘길 수 있다.
            - 또한 Trusted OS (or TA)는 해당 UA에 대한 정보가 없다.
            - 즉, Secure World가 Untrusted OS를 믿고 포인터를 따라가면 공격자가 의도한 메모리를 읽거나 덮어쓸 수 있음
        - 대응 방안: TA가 해당 포인터를 사용하기 전에, 해당 포인터가 정말로 해당 UA의 주소 공간에 속하는지, 접근 권한 (read/write)이 적절한지 체크해야 함 (=Pointer Sanitization)
    - PrOS [TMC]


> <span style="background-color:#e9d5b8">**TZ-RKP (TrustZone-based Real-time Kernel Protection)**</span> 
- **SMC (Secure Monitor Call)**
    - Normal World에서 Secure World로 제어를 넘기는 주요 인터페이스
- **NS bit (Non-Secure bit in memory transactions)**
    - ARM TrustZone에서 메모리 또는 장치 접근 시 그 접근이 Secure인지 Non-Secure인지를 구분해주는 하드웨어 레벨 비트
    - Secure World는 NS 영역을 접근 가능하지만, 반대는 불가능.
        - NS bit = 0 (Secure)로 설정되어 Normal World에서 접근 불가
- Control instructions, page table update functions은 **SMC(Secure Monitor Call)**을 통해  
Secure World의 **TZ-RKP로 trap (예외 호출)됨**
- **페이지 테이블은 read-only**로 매핑되므로 커널에서 직접 수정할 수 없음
    - MMU 설정을 통해, 커널에서 page table을 **수정하면 fault 발생**

## 13주차: Embedded System

> - EPOXY 논문 등에서 Return address attack [13]  
> - EPOXY - All protections [13]

- EPOXY: Protecting Bare-metal Embedded Systems With Privilege Overlays [S&P’17]

- Bare-metal 시스템의 메모리 구조에 따른 보안 취약점
    - Security Hardware: 보안 하드웨어가 제대로 사용되지 않거나 쉽게 우회 가능
    - Sensitive IO: 민감한 입출력 제어 레지스터가 항상 접근 가능.
    - Global Data, Stack: 모든 RAM 영역이 읽기/쓰기/실행 가능(WX), 즉 DEP(데이터 실행 방지) 적용 불가.
    - Code (Flash): “No ROP defenses”
    - 전체 시스템이 단일 권한 수준(privileged 모드)에서 실행

- 이러한 문제를 해결하기 위한 EPOXY의 핵심 기술
    - <span style="background-color:#e9d5b8">**◆Privilege Overlaying**</span>: 민감한 작업만 privileged 모드에서 수행하고 나머지는 unprivileged 모드로 실행.
        - `request privileges;` 민감한 연산이 필요한 부분만 분석을 통해 찾아내고 → 그 일부만 privileged 모드로 승격 후 작업
        - `drop privileges;`
    - Access Control using MPU: 민감한 IO, 보안 레지스터 접근을 제한.
    - <span style="background-color:#e9d5b8">**◆SafeStack 적용**</span>: return address 보호를 통한 stack smashing 방지.
        - ret 같은 데이터가 있는 기존 stack과 Unsafestack을 메모리 공간에서 분리함
        - **Stack**은 메모리의 높은 주소에서 **낮은 주소로 성장**
        - **UnsafeStack**은 heap 뒤에 위치하며, 낮은 주소에서 **높은 주소로 성장** (stack grow up)
        - 그리고 두 스택 사이에 MPU를 이용한 **Guard Region**을 두어, 오버플로우 접근을 감지
    - <span style="background-color:#e9d5b8">**◆Diversification (무작위화)**</span>: 코드와 데이터 레이아웃을 무작위화하여 코드 인젝션 및 ROP 공격을 방어
        - EPOXY 컴파일러가 동일한 source code에 대해 **다른 Seed 값**을 입력받아 **다른 Binary Layout을 생성**
            - 각각의 디바이스에 배포되는 실행 파일이 다르게 됨
        - RAM에 있는 .data, .bss, heap에 있는 **변수들**, Flash에 있는 **함수들**의 **순서(레이아웃)를 무작위로 배치**
        - **함수 사이에 Invalid execution, trap 함수 배치**
        - 특정 글로벌 변수를 노리는 공격 시, 오프셋 무작위화로 인해 정확한 위치 계산 불가.

| 메모리 영역  |  보호 기법                        | 대응 위협                         |
| ------------- | ------------------------------------------------------- | ------------------------------- |
| Security HW | Access Restriction (DEP), Privileged Overlay    | MPU 우회, 시스템 제어     |
| Sensitive IO  | Access Restricted, Privileged Overlay        | 인증 우회, IO 직접 조작     |
| UnsafeStack  | Stack 분리 및 Guard Region            | Stack Smashing, Code Injection |
| Global Data  | 무작위화로 Global Data Protected, RW-NX    | 전역 변수 변조, Code Injection |
| Stack          | SafeStack, MPU Protection             | Stack Smashing, ROP, Code Injection |
| Code (Flash) | RX only, Function Diversification            | Code Injection, ROP           |

## 14주차: Safe Language

- memory safe language의 보안 이슈

- **JavaScript**
    - 수동 메모리 할당/해제 없음 & 포인터 없음 & 배열 bound check함
    - JavsScript runtime이 취약함
        - Type Confusion Error
            - 중간에 타입을 바꿨는데, JIT 컴파일러가 이미 특정 타입에 맞는 연산(머신코드)으로 처리해버림
            - 동적 언어임에도 JIT 컴파일러가 이를 반영하지 못함
        - JIT Spray
            - 특정한 패턴을 가진 스크립트를 작성해 JIT 컴파일러가 공격자가 원하는 기계어(opcode) 시퀀스를 생성하도록 유도
- **WASM (web assembly)**
    - virtual machine 런타임에서 실행할 수 있는 binary instruction format ??
    - 머신 바이너리와 비슷한 속도로 런타임 수행 가능 → 단순한 형태이기 때문
    - 여러 low-level language를 지원해줌 (컴파일 타겟만 바꾸면 됨)
    - **Sandbox Execution 지원**
        - Managed Memory = safe memory
        - Linear Memory = unsafe memory
            - 여기서 Managed Memory나 다른 모듈의 메모리로 넘어가는건 막아줌
    - **Control Flow Integrity**
        - function index, function type 기반 검증 수행
    - **CAGE [CGO’25]: ARM MTE 및 ARM PAC 활용한 WASM 보안성 향상◆**
        - <span style="background-color:#e9d5b8">**ARM MTE**</span>를 활용한 Memory Safety
            - Heap memory object / stack frame 할당시마다 random한 memory tag를 부여 + 사이에 guard region 삽입
        - <span style="background-color:#e9d5b8">**ARM PAC**</span>을 활용한 function pointer reuse 대응
            - Wasm 환경에서는 여러 인스턴스가 존재하고, 각각이 공유된 function table을 사용하므로, reuse 공격이 더 쉬움
            - PAC modifier를 인스턴스마다 다르게 설정함으로써, 다른 인스턴스에서 생성된 포인터는 인증에 실패하게 만들어 function pointer reuse 공격을 방지
    - **Swivel [Security’21]: 머신코드를 대상으로 하는 Spectre 공격 및 대응**
        - Spectre-PHT: conditional branch에 대한 예측 실행으로 특정 코드가 실행되면서 예상치 못한 cache 변화 발생

- **Rust: 가장 memory safe language**
    - 배열 접근시 bound check 자동 삽입
    - **ownership 시스템을 도입하여 temporal memory safety 구현**
        - 각 값이 하나의 owner만 가질 수 있기 때문에 use-after-free 방지
    - **TRust[Security’23]◆**
        - Unchecked codes: 1) unsafe 영역에 있는 코드, 2) 다른 언어로 작성된 외부 라이브러리의 코드
        - 이를 방어하기 위한 in process isolation 도입
            - **Applies <span style="background-color:#e9d5b8">SFI</span> to isolate from unsafe code, and <span style="background-color:#e9d5b8">MPK</span> to isolate from external libraries**
    - ERASan[S&P’24]: 코드 분석을 통해서 raw pointer에 대해서만 Address Sanitizer 적용해서 메모리 에러 탐지
